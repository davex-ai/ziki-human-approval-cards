Ziki Human Approval Cards

Give every meaningful agent action a structured, evidence-backed review card so a human can approve, reject, edit, or ask for more evidence before anything high-impact is executed.

Note: This is an illustrative prototype. Names, numbers, issue IDs, evidence, and outcomes are demo data and are not connected to Ziki production systems.

2. The problem

Ziki supports agents with different roles and permissions, but a human may not understand exactly what an agent is about to do before the action changes bids, validations, claims, ownership, issue state, or public project links. Today the human usually sees that something happened after the fact: a bid appeared, a report was cleared, a pull request was linked, a validation was submitted. By then the cost of being wrong has already been paid.

The gap is not permissions. Permissions answer "is this agent allowed to do this?" The gap is consent and comprehension: "what exactly will this agent do right now, based on what evidence, and can I undo it?" Without a structured preview, reviewers either approve blindly, block useful work, or revert to reading raw diffs and logs to reconstruct intent.

3. What Ziki already does well

Ziki's role model is a genuine strength. Distinct roles such as Reviewer, Contributor, and Triager already map to real capabilities, and permission checks keep agents inside the boundaries of their role. Issues carry state, claims, and history, so there is a durable record of what happened. Bids and validations already encode structured, machine-readable intent rather than free-form chat messages.

The proposal builds on those strengths instead of replacing them: the approval card is a thin presentation and consent layer over the permission system that already exists.

4. Where human-agent interaction breaks down

  • Intent is implicit. An agent acts, and the human infers intent from the result instead of reading a stated proposal.
  • Evidence is scattered. The reasoning behind an action lives in logs or a conversation, not next to the action itself.
  • Risk is invisible. Submitting a validation and clearing someone else's duplicate report look identical in a notification list.
  • Reversibility is unknown. The human cannot tell at a glance whether saying yes can be undone in one click or needs a new, awkward repair action.
  • Decisions are not recorded. When a human does intervene, the reason is rarely captured, so the agent gets no structured feedback and the audit trail stays thin.

5. The proposed Human Approval Card model

Introduce a structured Human Approval Card for meaningful state-changing actions. The card is a reviewable contract between the agent and the human: the agent commits to an exact payload and the evidence behind it, and the human answers with approve, reject, or "show me more" before anything executes.

The card is not a chat message. It is a typed object with a stable schema, rendered the same way for every agent, so a reviewer learns one layout and can scan any proposal in seconds. Read-only actions never produce a card; they run immediately. Only actions that change state in the world — bids, validations, claims, ownership, points, issue transitions, public links — are gated behind a card.

5.1 Approval card fields

Agent identity
Who is proposing: display name and avatar or initials.
Agent role
The role acting on the proposal, shown next to the required permission so mismatches are obvious.
Proposed action
A short human-readable description of the intent, e.g. "Submit solution bid".
Exact payload
The literal object that would be sent, shown as readable JSON or key-value pairs — not a paraphrase.
Evidence
The concrete findings that justify the action: file paths, counts, diffs, test output. Short on the card, complete in the detail view.
Required permission
The permission the action needs, alongside the agent's actual permission check result.
Risk
Low, Medium, or High, derived from the action class rather than guessed by the agent.
Expected impact
One sentence describing what changes in the world if the human says yes.
Reversibility
Reversible, Reviewable, or Hard to reverse — how costly a wrong "yes" is.
Expiry
How long the proposal stays valid. An expired card cannot execute and must be re-proposed.

6. Card anatomy

A card is a compact, scannable object: agent avatar or initials, agent name and role, issue number and title, the proposed action, risk and blocking badges, a one-line reason, a short evidence summary, required permission, expected impact, reversibility label, and a timestamp. The primary action button and a secondary Reject button sit at the bottom; a detail view holds the full evidence list, the exact payload, the permission check, the risk and reversibility explanations, and any warning about claims, ownership, issue state, or public links. Long paragraphs never appear on the card face — they live in the expandable detail view.

7. Approval flow

7.1 Action classes

  • Read-only actions can run immediately, without a card and without friction.
  • Low-risk reversible actions may use optional approval: they can run by default, but a card is still produced so the human can see and optionally intervene.
  • High-impact actions require explicit approval; nothing executes until a human confirms.
  • Actions involving claims, ownership, points, public links, or issue state require explicit approval regardless of how routine they look, because they affect other people's work.

7.2 Steps

  1. The agent prepares a proposal with evidence and an exact payload.
  2. The card appears in the human's approval center in a pending state.
  3. The human reviews the card: evidence, payload, permission check, risk, reversibility.
  4. The human chooses one of:
    • Approve — after a confirmation step showing the exact payload, the action executes.
    • Reject — with a required reason that is returned to the agent.
    • Request more evidence — the card moves to "more evidence requested" and the agent supplies what is missing.
    • Edit — the human may adjust the payload before approving; the edit is recorded alongside the original proposal.
  5. The decision, the payload actually sent, and the resulting API response are written to the audit trail.

8. Risk and reversibility rules

  • Low risk / Reversible — informational actions that can be redone or withdrawn freely, e.g. submitting an independent validation.
  • Medium risk / Reviewable — actions that are visible to others but can be audited or superseded, e.g. placing a bid that can be withdrawn.
  • High risk / Hard to reverse — actions touching claims, ownership, triage state, points, or public links; they affect other contributors and need a deliberate new action to undo.

Blocking cards stop the pipeline: while a blocking card is pending, the agent does not continue down that path. Non-blocking cards can be left to age while other work proceeds.

8.1 Safety rules

  • The approved payload must match what the human saw.
  • An expired approval cannot execute.
  • An agent cannot approve its own proposal.
  • A human rejection must include a reason.
  • Batch approval must be limited to clearly equivalent actions.
  • Read-only access must remain available without unnecessary friction.

9. Audit trail

Every proposal and decision should be recorded with the original proposal, human edits, final payload, approver, timestamp, and resulting API response. The audit trail answers three questions after the fact: what the agent intended, what the human actually authorized, and what the system did. In this prototype the timeline is local and simulated; in production it would be a persisted, append-only log readable from both the issue and the approval center.

10. Example user walkthrough

  1. Open the approval center. Four actions are waiting; two of them are blocking.
  2. Alex proposes an independent validation on issue #1151 with two evidence items. The card is low risk and non-blocking, so you press Approve validation, read the exact payload in the confirmation dialog, and confirm. The card turns green and an approval entry appears in the audit trail.
  3. Ryan proposes clearing a duplicate report on #520. The card is high risk and blocking, so the primary button opens the detail view first: evidence, payload, permission check, risk explanation, reversibility, and a warning that the action changes issue state. You decide the evidence is thin and use Request more evidence, describing what is missing. The card becomes "More evidence requested" — neither approved nor rejected.
  4. Seraphine's bid on #1151 is medium risk. You reject it with the reason "Split the fix into two smaller bids so the config change can be reviewed separately." The reason appears on the card and in the timeline.
  5. You filter by Blocking to see only what stops work, then press Reset demo to restore the original state and try a different path.

11. Implementation approach

  1. Schema first. Define the approval card as a typed object (agent, role, action, payload, evidence, permission, risk, impact, reversibility, expiry) and validate every proposal against it at the API boundary.
  2. Action classification. Tag each API operation with a class (read-only, low-risk reversible, high-impact, ownership-sensitive) so risk is derived centrally instead of by each agent.
  3. Queue and expiry. Pending cards live in a per-project queue with expiry timestamps; expired cards are invalidated before execution.
  4. Confirmation gate. Execution requires a signed decision record referencing the exact payload hash the human saw.
  5. Progressive delivery. Start with the highest-impact classes (claims, ownership, issue state, public links), then widen as reviewer trust grows.
  6. Accessibility from day one. Real buttons, labelled dialogs, Escape to close, focus return, and live regions — the same bar this prototype meets.

12. Out of scope

This prototype does not implement:

  • Real Ziki authentication.
  • Real API calls.
  • Real GitHub operations.
  • Real claims, bids, points, or issue updates.
  • Production persistence.
  • Automatic agent training or long-term memory.

Everything in the demo runs in the browser against local sample data. No credentials are requested, stored, or transmitted.

13. Acceptance criteria

  • [ ] Humans can see what an agent wants to do before execution.
  • [ ] The card identifies the agent and role.
  • [ ] Evidence and exact payload are visible.
  • [ ] Risk and reversibility are visible.
  • [ ] High-impact actions require explicit confirmation.
  • [ ] Humans can approve, reject with a reason, or request more evidence.
  • [ ] The demo records decisions in a local audit timeline.
  • [ ] The prototype is usable by keyboard and screen-reader users.
  • [ ] The prototype clearly states that it uses illustrative data.
